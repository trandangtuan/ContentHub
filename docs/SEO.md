# SEO

SEO is implemented as one package, `packages/seo`, that both `apps/web`
(for HTML) and any future consumer use as the single source of truth for
URL shapes, metadata, robots rules, JSON-LD, sitemaps, and llms.txt. This
document explains the design; `packages/seo/src/*.test.ts` is the
executable spec.

## URL structure

`packages/seo/src/canonical.ts`'s `paths` object is the **only** place a
`/truyen/...`-shaped URL is constructed. Every page, every JSON-LD builder,
every sitemap provider imports `paths.story(slug)` etc. instead of
string-templating a URL inline — so a route change is a one-file edit.

```
/                                    home
/truyen                              story list
/truyen/[story-slug]                 story
/truyen/[story-slug]/[chapter-slug]  chapter
/tac-gia                             author list
/tac-gia/[creator-slug]              author
/the-loai                            category list
/the-loai/[category-slug]            category
/tag/[tag-slug]                      tag
```

Route params are never used as the canonical identifier
(`/story?id=123` never exists) — slugs are the URL, generated by
`packages/shared`'s `slugify` (Unicode-normalized, lowercase, `đ/Đ`-aware
since NFD doesn't decompose them) and made unique by `disambiguateSlug`
retries against the DB's unique constraint.

## Canonical URLs

`buildCanonicalUrl(config, path)` strips **every** query string and hash
fragment — `?utm_source=`, `?ref=`, `?sort=`, `?page=` never produce a
distinct canonical page (spec §10). This is deliberate even for pagination:
a paginated `/truyen?page=2` still canonicalizes to `/truyen`, per the
spec's explicit list of params that must never fork a canonical.

## Metadata

`packages/seo/src/metadata.ts`:

- `titleTemplates` implements the exact templates from spec §12 (`{Story
  Title} – {Site Name}`, `{Chapter Title} – {Story Title} – {Site Name}`,
  `{Author Name} – Truyện và tác phẩm – {Site Name}`).
- `buildStoryDescription` uses the creator's description/short description,
  truncated by `packages/shared`'s `truncateText` — which walks Unicode
  code points (`Array.from`), never splits a surrogate pair, and prefers to
  cut at the nearest word boundary.
- `buildChapterDescription` is **title + story title + a short excerpt**,
  never the full chapter body (spec §13) — the excerpt itself is truncated
  to ~90 characters before being embedded.
- `buildPageMetadata` assembles the final object (title, description,
  `alternates.canonical`, `robots`, `openGraph`, `twitter`) in the exact
  shape Next's `generateMetadata()` return type expects — `apps/web` pages
  cast the result to `Metadata` and return it directly.

## Robots

`getRobotsMetadata(page)` (spec §30) is the single function every page's
`generateMetadata` calls to decide `index`/`follow`. It only returns
`index: true` for `{ kind: "content", status: "PUBLISHED", visibility:
"PUBLIC" }` (unless `seoNoindex` is set) or `{ kind: "static-indexable" }`
(homepage, list pages). Dashboard/admin/auth pages, drafts, private/unlisted
content, and thin taxonomy pages (a tag with <2 stories) all resolve to
`noindex`. `apps/web`'s route handlers and pages call this instead of
assuming "public route = indexable."

`buildRobotsTxt` generates the actual `robots.txt` content; `app/robots.ts`
uses Next's `robots()` convention but delegates the actual rule *values* to
the same builder so the two never drift. Public content paths are always
`Allow`ed; `/dashboard/`, `/api/`, `/admin/`, `/auth/`, `/login/`,
`/register/` are always `Disallow`ed. **AI crawlers are not blocked by
default** (spec §68) — `ROBOTS_DISALLOWED_AGENTS` (env) is how an operator
opts into blocking specific ones.

## Structured data (JSON-LD)

`packages/seo/src/jsonld.ts` builds:

- `Book` (story pages) — `CreativeWork` is available for content types
  where `Book` doesn't fit, but nothing currently uses it since only STORY
  is enabled.
- `Person` / `Organization` (author pages — `Organization` when
  `creator_profiles.is_organization` is true).
- `BreadcrumbList` (every story/chapter/author/category/tag page).
- `WebPage` (homepage and other pages without a more specific type).

`packages/seo/src/breadcrumbs.ts`'s `breadcrumbs` object builds the same
trail data (`{ name, path }[]`) that both the JSON-LD `BreadcrumbList` and
the rendered `<nav className="breadcrumb">` use — one source of truth so
the visible breadcrumb and the structured data can never disagree.

Rendering: `apps/web/src/components/JsonLd.tsx` serializes with
`JSON.stringify` (which already escapes quotes) and additionally escapes
`<` to prevent a value containing `</script>` from breaking out of the tag.

## Sitemaps

`packages/seo/src/sitemap.ts` defines the `SitemapProvider` interface
(`{ key, getUrls(cursor?) }`) and pure XML builders
(`buildSitemapXml`/`buildSitemapIndexXml`) — no Prisma import, so it's
independently unit-testable. `apps/web/src/lib/sitemap-providers.ts`
implements the interface per URL family (`StorySitemapProvider`,
`ChapterSitemapProvider`, `AuthorSitemapProvider`,
`CategorySitemapProvider`, `TagSitemapProvider`), each querying only
`PUBLISHED`/`PUBLIC`/non-deleted rows.

`/sitemap.xml` (`apps/web/src/app/sitemap.xml/route.ts`) is an **index**,
not one giant file (spec §18): it lists `/sitemap-pages.xml`,
`/sitemap-stories/1..N`, `/sitemap-chapters/1..N` (N computed from a cheap
`COUNT(*)` query, not by paging through every row), plus
`/sitemap-authors.xml`, `/sitemap-categories.xml`, `/sitemap-tags.xml`.
Story/chapter pagination is page-number-based
(`MAX_URLS_PER_SITEMAP = 10_000`, well under Google's 50k limit) with a
single bounded `LIMIT/OFFSET` query per page — never loads the whole table
into memory. Every entry has `loc` + `lastmod` only; `changefreq`/
`priority` are never emitted since neither builder has real values for
them (spec §19).

`TagSitemapProvider` only yields a tag once it has ≥2 published stories —
a thin tag gets a page (so the handful of readers who find it aren't
broken) but stays out of the sitemap and is `noindex`ed (spec §45).

All sitemap/llms/story/category/author/tag routes are marked `export const
dynamic = "force-dynamic"` — Next would otherwise try to statically
pre-render them at *build time* (with whatever data existed then, frozen
until the next deploy), which is wrong for a platform whose whole point is
showing live "latest chapter" data, and would also make `next build` fail
in any environment without a database reachable at build time (like a CI
image build). This was caught by running a full `next build`, not just
`tsc --noEmit`.

## llms.txt / llms-full.txt

`packages/seo/src/llms.ts` builds both files from `SeoConfig` (+ aggregate
stats for the "full" version) — never a database dump. `llms.txt` states
what the site is, its public URL patterns, content policy, and attribution
expectations; `llms-full.txt` adds aggregate counts and top categories.
Both are tested to *not* contain sensitive terms (wallet, revenue,
moderation, email) as a guard against someone later adding a field that
leaks internal state into a document that's deliberately public and
unauthenticated.

## Redirects and 404/410

`packages/seo/src/redirects.ts`: `buildSlugChangeRedirect(oldPath,
newPath)` is called by `apps/api`'s story-update handler whenever a title
change produces a new slug — the redirect row is written in the same
transaction as the slug change (spec §31), so the old URL 301s instead of
404ing. `resolveNotFoundStatus(reason)` maps `"permanently-deleted"` to
`410` and everything else to `404` (spec §32); `apps/api`'s public routes
implement this distinction and are tested for it. `apps/web`'s pages
currently only call Next's `notFound()` (always 404) for both cases — see
docs/ARCHITECTURE.md's "Implementation status" table for why that gap
exists and what closing it would take.

## Search

`packages/search`'s `SearchProvider` interface is implemented by
`PostgresSearchProvider` using `contents.search_vector` (a `tsvector`
maintained by a Postgres trigger — see
`packages/database/prisma/migrations/20260921063600_search_vector_trigger`),
searching title/short_description/description only — never chapter bodies
via `LIKE` (spec §55). Swapping to OpenSearch/Elasticsearch later means
writing a second class against the same interface; nothing that calls
`SearchProvider.search()` needs to change.

## Performance / Core Web Vitals

The chapter reader (`apps/web/src/app/truyen/[storySlug]/[chapterSlug]/
page.tsx`) is a Server Component with no client-side data fetching for the
main content, no dashboard/editor code in its bundle (dashboard is a
separate route tree), and its cover image uses `priority` (not lazy) since
it's typically the LCP element, while in-chapter images would use default
lazy loading. Analytics/recommendations/comments are intentionally not
built into this pass — see docs/ARCHITECTURE.md's implementation-status
table — but the architectural rule (don't block first paint on them) is
already encoded in the page not importing them.
